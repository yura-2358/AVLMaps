# 設計判断ログ（実装前に必ず確認）

このファイルは、卒検の実験計画を検討する過程で決まった方針とその根拠をまとめたもの。実装中に「なぜこうなっているか」を確認したいときはここを見る。より詳細な議論はClaude Projectの「実験計画の評価.md」にあるが、ここには実装に直結する結論のみをまとめてある。

## 1. 忘却モデルのスコープ縮小

- **決定**: 忘却手法は1つ（2値閾値削除など実装が最も軽いもの）のみ実装する。2値削除/線形減衰/エビングハウス忘却曲線の3手法比較実験は卒検スコープ外とし、今後の課題として明記する。
- **理由**: 著者自身が「短期・単純な実験ではエビングハウスの優位性は出ない」と予測しており、投入労力に対する情報獲得の期待値が主実験（条件1〜3）より低い。ただし忘却機構自体は中間報告書3.3節で3本柱の1つとして説明済みのため、完全にゼロにはせず最低限のシステムとしての体裁は保つ。

## 2. AVLMaps実装の進め方

- **決定**: AVLMaps公式コード（github.com/avlmaps/AVLMaps, github.com/vlmaps/vlmaps）を最初に読み、動かすところから着手する。一から論文だけを見て再実装しない。
- **理由**: 実験計画の全条件がAVLMapsとの比較で成立しており、ベースライン数値が無いと何も比較できない。また環境構築・評価ハーネスを既知のリファレンス実装で先に検証できる。

## 3. Static Mapの共通化

- **決定**: Object Localization / Area Localizationなど研究の新規性でない部分は、AVLMapsベースラインと提案手法で完全に共通のコードを使う。変えてよいのは統合ロジック（AVLMapsのヒートマップ掛け合わせ的な統合 → 提案手法の明示的ベイズ推定）のみ。
- **理由**: 比較の公平性。Static Map側が独自実装だと、精度差が新規性（動的音声処理・ベイズ統合）によるものか実装差によるものか切り分けられなくなる。
- **注意**: SAM3のようにAVLMaps原論文より新しいモデルを使う場合、ベースライン側にも同じアップグレードを適用すること。片方だけ新しいモデルにすると比較が汚染される。

## 4. Dynamic Mapのセグメンテーション方式

- **決定**: まず無音検出（音量閾値ベース、AVLMaps方式）を実装する。実環境ノイズで誤検出が問題になった場合のみYAMNet等の分類ベース検出に切り替える。
- **理由**: AVLMaps原論文は音量閾値ベースの無音検出を使っている（YAMNetのような分類モデルではない）。これに揃えることで比較の公平性を保てる。ただしAVLMapsの無音検出はクリーンな合成音声でしか検証されていないため、本研究の実環境録音で問題が出た場合はYAMNet等への切り替えが正当化できる。
- **オプション**: 無音検出で境界検出し、切り出したセグメントをYAMNetでフィルタするハイブリッドも可。

## 5. シミュレーション不使用・実機（HSR）のみで実験

※2026-10-22注記: 「実機のみ・シム不使用」は有効のまま。使用ロボットはHSR→sobit_eduへ変更（決定12）。

- **決定**: Habitat/Matterport3Dのセットアップ（データセット利用申請等）は行わない。実機（HSR）のみで実験する。
- **理由**: 本研究はDOA推定を含む本物の動的音声処理を扱うため実機実験が前提になる。AVLMaps自体もHabitat上・実機上いずれでも音声を動画に事後合成しているだけで、音響伝搬をモデル化した意味のあるデータは得られない（本格的な音響シミュレーションにはSoundSpaces等の別統合が必要でAVLMapsには含まれない）。Matterport3Dの利用申請・python2スクリプトなどの手続きコストに見合わない。

## 6. プラットフォームはHSR、ベースラインもHSRに移植

※2026-10-22注記: プラットフォームはsobit_eduへ変更（決定12）。「ベースラインも提案手法と同一ロボットに載せ、インターフェース層のみ移植」原則は不変。

- **決定**: AVLMapsベースラインも提案手法と同じくHSR上で動かすように移植する。移植するのはロボットとのインターフェース層（ROSトピック購読、TF/座標系、ナビゲーション呼び出し）のみで、アルゴリズムのコアは共通化する（決定3と同じ原則）。
- **理由**: AVLMaps原論文の実機実験はRidgeback+Panda+RealSense D435であり、HSRではない。プラットフォームが違うと比較にならないため、ベースラインもHSRに載せ替える必要がある。

## 7. HSRBのマイク構成とTAMAGO追加

※2026-10-22注記: sobit_eduにHSRB標準PS Eye直列4マイクなし→前提消滅。マイクはTAMAGO（8ch円形）のみ想定（決定12）。下記は経緯として保持。

- **状況**: HSRB標準搭載のPlayStation Eye内蔵直列4マイクは、原理的に前後の音源位置を区別できない（コーン・オブ・コンフュージョン）。これを解消するため外付けTAMAGO（円形/球形マイクアレイ）の追加を検討中。
- **推奨検証**: 前後対称な既知角度（例: 0度と180度）から音を鳴らし、直列4マイクのみでは混同すること、TAMAGO追加後は区別できることを単体テストとして明示的に確認する。

## 8. ベースライン(AVLMaps)を実環境録音で評価することの妥当性

- **決定**: AVLMapsを実環境録音（本物の音響伝搬・残響・ノイズを含む条件）で評価してよい。AVLMaps原論文では合成音声条件でしか検証されておらず、精度が下がることが予想されるが、これは研究の問題意識（AVLMapsの静的前提が実世界で崩れる）を裏付ける正当な結果であり、恣意的にベースラインを弱く見せる行為ではない。
- **フェアネス条件**: AVLMaps側の実装・チューニングを手抜きしないこと（新規性と無関係な部分でAVLMapsだけ不利にしない）。卒論本文で「AVLMaps原論文は合成音声条件で評価されているが、本研究は実環境録音で評価する。これは静的・既知の音源位置という前提が実世界でどこまで成立するか検証するため」と明記すること。
- **余力があれば**: AVLMapsを原論文と同じ合成音声条件でも動かし、報告値に近い性能を再現できるか確認するサニティチェックを行う（実装が悪いのか条件が変わったからなのかを切り分けるため）。

## 9. 実装バグと研究上の本質的な限界の切り分け方針

- **方針**: 完全な保証は不要だが、以下の段階的検証は行う。
  1. 各モジュールを正解のわかる簡単な条件で単体テスト（DOA: 既知角度0/90/180/270度、前後対称位置でのTAMAGO効果検証を含む）。
  2. 簡単な条件（静かな部屋、単一音源、近距離）から難しい条件へ段階的に評価。
  3. trivialな比較対象（ランダム推定、DOA補正なしの生角度）を用意し、それを下回っていないか確認。
  4. 最終誤差だけでなく、検出セグメント・DOA生角度・von Misesパラメータ・個別/統合後のヒートマップを可視化・ログ保存する。
  5. AVLMapsを原論文条件でも動かすサニティチェック（決定8参照）。
- **重み付け**: 条件1・3（研究の中心的主張）は重点的に検証する。忘却モデル比較のような周辺実験はそこまで厳密でなくてよい。

## 10. Dynamic Map音源定位（DOA推定）エンジンの選定

- **決定**: DOA推定にはODAS（`odas_ros`）を採用する。colcon_ws内に既にROS2ラッパー（`odas_ros`、`odas_ros_msgs`、`odas_wav`）が用意されており、これを軸に統合検証を進める。
- **理由**: AVLMaps原論文にDOA推定の実装はなく（`researchoverview.md`参照）、本研究で新規に統合する要素だが、ゼロから実装するのではなく確立済みライブラリの統合作業として位置づける。比較候補としてHARK（`HARK_Tutorial_2025`でPS Eye/TAMAGO両方のマイクチュートリアルを実施済み、pyhark同梱）もあったが、ROS2統合済みのODASを軸とする。
- **付記**: HARK関連資産（PS Eye/TAMAGOチュートリアル一式）は直接使用しないが、マイク前後分離性能の参考実験（決定7参照）に転用可能なため保持しておく。

## 11. ベースライン（AVLMaps）音声セグメンテーション方式の定義（2026-09-23）

- **決定**: 本研究でいう「AVLMaps方式」の音声セグメンテーション＝AVLMaps公式コード**実機用経路**の方式。Habitat用経路の方式でない。
- **理由**: 本研究Habitat不使用（決定5）。実機実験の比較対象として意味を持つのは実機用経路。
- **コード上の実体**（2026-09-23確認）:
  - 実機用経路 `create_audio_map_batch_real` / `create_audio_map_batch_real_with_clip`（`avlmaps/utils/audio_mapping_utils.py`）: `segment_audio_with_silence`（音量閾値ベース無音検出）呼出しコメントアウト済み。セグメント区間は引数`time_ranges`（シーケンス毎`[start, end]`秒リスト）で**外部から与える**。リポジトリ内に呼出元なし＝区間の生成方法はコード外（原論文では音声合成時の既知区間）
  - Habitat用経路 `create_audio_map_batch`: `segment_audio_with_silence`使用。論文本文記述（"Whenever the volume is above a threshold..."）はこちら対応
  - → 本研究ベースラインのセグメンテーション＝**既知区間（`time_ranges`）入力方式**
- **帰結・注意**:
  - `time_ranges`、ベースラインにとって正解区間相当（oracle）。提案手法側（決定4、無音検出等で自前検出）よりセグメンテーション面で有利な条件。ベースラインを弱く見せる方向でないためフェアネス上の問題は小さいが、卒論で「ベースラインは既知区間を入力」と明記要
  - 決定4の根拠「AVLMaps原論文が音量閾値ベース無音検出→これに揃える」、本決定で前提が変化（論文本文記述とは一致、実機コードとは不一致）。決定4自体の見直し要否は未決（下記未決事項）
  - 実機用経路は現行データ収集出力（`poses.txt`/`timestamps.txt`/`audio.wav`/`audio_timestamps.txt`）と非互換（`audio_video/<seq>/audio_video.mp4`・`pose/`・`rob2cam_tf.txt`前提）。変換層要
  - 実機用経路`create_audio_map_batch_real`は`nr.reduce_noise`（noisereduce）呼出すが`noisereduce`未import・`/opt/pytorch/.venv`未install→現状そのまま呼ぶとNameError。ノイズ除去も実機用経路の一部としてベースラインに含める
  - 実機用経路のバグ疑い（2026-09-28発見）: `time_ranges`（秒）→映像フレーム番号（秒×fps）変換値で音声サンプル列をスライス（`audio_mapping_utils.py:237-242`）。修正する場合も方式定義（既知区間入力）は不変、修正内容を記録してベースラインに適用（決定8「手抜きしない」）。詳細strategy.md B6
  - ※2026-10-22注記: 上記バグ疑い箇所は新規関数`create_audio_map_hsr`で置換→踏まない（strategy.md B6）

## 12. 使用ロボットをHSR→sobit_eduへ変更（2026-10-22）

- **決定**: ベースライン（AVLMaps）・提案手法とも実機はsobit_edu（TeamSOBITS、TurtleBot2/Kobuki差動二輪ベース＋ASUS Xtion＋Hokuyo URG＋Dynamixel頭部/アーム）で実験。HSRは使わない。
- **理由**: TAMAGO接続方法の観点（ユーザー決定）。
- **帰結**:
  - フェアネス原則（決定3・6）は不変: 両手法とも同一ロボット（sobit_edu）・同一センサ・同一コード。
  - HSR上で得たB1（RGB-D収集）・B3（VLMap）・B4（nav2結合Stage1〜3）・B5（AreaMap）の実機結果・データはsobit_eduで再取得要。コード・手順・知見（座標変換・Python環境・SoundMap実装等）は流用。
  - マイク: HSRB PS Eye直列4マイク前提（決定7）消滅、TAMAGOのみ。
  - 時刻同期: TAMAGO・Xtionとも同一PC接続→HSR⇔PC時計ずれ問題は構造上解消見込み（ただしXtion `use_device_time`の影響は実測要、strategy.md）。
  - 名称: `hsr_data_collector.py`・`HSRLangRobot`・`hsr.yaml`・`create_audio_map_hsr`等HSR名残存。パラメータ切替で動作見込み、改名は任意（未決）。
